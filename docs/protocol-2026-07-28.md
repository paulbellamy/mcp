# MCP 2026-07-28 (stateless protocol) support

This document describes how the CLI supports protocol revision `2026-07-28`
("stateless MCP", announced 2026-07-28 on blog.modelcontextprotocol.io) while
remaining compatible with legacy servers that require the `initialize`
handshake, and lays out the test suite that verifies the behavior.

## What changed in the protocol

Revision `2026-07-28` turns MCP into a stateless request/response protocol:

- The `initialize`/`notifications/initialized` handshake and the
  `Mcp-Session-Id` header are gone. Every request carries its protocol
  version and client capabilities in `_meta`
  (`io.modelcontextprotocol/protocolVersion`,
  `io.modelcontextprotocol/clientCapabilities`, and optionally
  `io.modelcontextprotocol/clientInfo`).
- `server/discover` is a mandatory server RPC advertising
  `supportedVersions`, capabilities, and identity. Clients may call it up
  front, and should use it as the backward-compatibility probe on stdio.
- Streamable HTTP requests must carry `MCP-Protocol-Version` (matching the
  `_meta` value), `Mcp-Method` (the JSON-RPC method), and — for `tools/call`,
  `resources/read`, and `prompts/get` — `Mcp-Name` (the tool/prompt name or
  resource URI). Header values outside the safe ASCII range use the
  `=?base64?...?=` sentinel encoding.
- Every result carries a `resultType`: `"complete"` for ordinary results and
  `"input_required"` for Multi Round-Trip Requests (MRTR). Results from
  earlier-protocol servers that omit the field are treated as `"complete"`.
  MRTR replaces server-initiated requests (sampling/elicitation/roots): the
  server returns `inputRequests` and/or an opaque `requestState`; the client
  retries the original request (with a new request id) echoing
  `requestState` and providing `inputResponses`.
- List/read results carry `ttlMs` and `cacheScope` freshness hints.
- New spec error codes: `-32020` HeaderMismatch, `-32021`
  MissingRequiredClientCapability, `-32022` UnsupportedProtocolVersion
  (whose `data.supported` lists the server's versions). Resource-not-found
  moved from `-32002` to `-32602`.
- `ping`, `logging/setLevel`, SSE resumability (`Last-Event-ID`), and the
  HTTP GET stream are removed; `subscriptions/listen` replaces the GET
  stream for opted-in change notifications.

## How the CLI implements it

### Era negotiation (`negotiateProtocol`)

Connecting (`mcpConnect`) no longer starts with `initialize`. Instead the CLI
probes with `server/discover`, carrying full modern `_meta` (and, on HTTP,
modern headers):

- **Success** and `supportedVersions` contains `2026-07-28` → the transport
  is wrapped in a `protocolSession` that injects `_meta` into every
  subsequent request. No handshake is sent, and on HTTP no session id is
  used.
- **`UnsupportedProtocolVersionError` (-32022)** → the server is modern but
  does not speak our version. Per spec we do *not* fall back to `initialize`;
  the error surfaced to the user lists the server's supported versions.
- **Any other error** (JSON-RPC `-32601`, an HTTP `400/404/405/406` whose
  body is not a recognized modern error, a "server not initialized" error, a
  stdio probe timeout) → the server is legacy: fall back to the
  `initialize` (protocol `2025-03-26`) + `notifications/initialized`
  handshake, exactly as before this change. Session ids keep working on
  HTTP in this mode.
- Transport-level connection failures are surfaced immediately (a legacy
  handshake over the same broken transport cannot succeed either).

The era decision is cached for the lifetime of the process (which is also
the lifetime of the connection), matching the spec's guidance. The daemon
performs the same negotiation when it spawns or respawns a stdio server, so
requests forwarded through the daemon are decorated for modern children and
passed through untouched for legacy children.

`mcp ping` uses `server/discover` as the liveness check against modern
servers (`ping` was removed from the protocol) and `ping` against legacy
servers.

### Stateless requests (`protocolSession`)

`protocolSession` wraps a `Transport`. On every `Send`/`SendStreaming` it
converts the request params to an object (creating one when the request had
none — modern requests must always carry `_meta`) and merges in:

- `io.modelcontextprotocol/protocolVersion`: the negotiated version
- `io.modelcontextprotocol/clientCapabilities`: `{}` (the CLI declares no
  sampling/elicitation/roots support, so compliant servers must not send
  those input requests)
- `io.modelcontextprotocol/clientInfo`: `{"name": "mcp-cli", ...}`

Existing `_meta` keys (e.g. `progressToken`) are preserved.

### Modern HTTP headers

When the negotiated era is modern, `HTTPTransport` sends
`MCP-Protocol-Version`, `Mcp-Method`, and (for `tools/call`,
`resources/read`, `prompts/get`) `Mcp-Name` on every POST, applies the
base64 sentinel encoding when a name/URI is not header-safe, never sends
`Mcp-Session-Id`, ignores any session id the server mints, and skips the
legacy DELETE on close. Legacy mode behaves exactly as before.

### resultType and MRTR

`tools/call` and `resources/read` (the MRTR-capable requests the CLI makes)
handle the result envelope:

- absent or `"complete"` → the result is rendered as before (legacy
  compatibility).
- `"input_required"` with `inputRequests` → the CLI declares no client
  capabilities, so this is surfaced as a structured tool error explaining
  that the server requested interactive input (listing the requested
  methods) rather than a hang or a crash.
- `"input_required"` with only `requestState` → the request is retried
  (fresh JSON-RPC id, `requestState` echoed verbatim, at most 5 rounds)
  per the MRTR client requirements.
- any other `resultType` → invalid per spec; a clear error is returned.

List responses ignore `resultType` (the spec forbids `input_required`
there).

### Caching

`tools/list` responses that carry `ttlMs` bound the tools cache freshness:
the effective TTL is `min(10m default, server ttlMs)`. Responses without
`ttlMs` keep the 10-minute default. `cacheScope` does not change behavior —
the cache is already private and per-user.

### Out of scope (follow-ups)

- `x-mcp-header` custom parameter mirroring (`Mcp-Param-*` headers) and the
  associated tool-definition validation/rejection in `tools/list`.
- `subscriptions/listen` (the CLI is one-shot; it never consumed the legacy
  GET stream either).
- Fulfilling `inputRequests` (form-mode elicitation on the terminal could
  come later; today the CLI declares no capability, so servers must not
  send them).
- CIMD client registration and RFC 9207 `iss` validation in the OAuth flow.

## Test suite plan

The suite follows the repo's existing style: unit tests against
`mockTransport`, HTTP tests against `httptest` servers, plus the
stdio/daemon integration tests. New fixtures include a *modern* mock server
(asserting on headers and `_meta`, answering `server/discover`) alongside
the existing legacy mocks (which answer `-32601` to unknown methods — the
realistic legacy behavior the fallback relies on).

### 1. Era negotiation (`negotiate_test.go`)

| Case | Server behavior | Expected |
|---|---|---|
| modern stdio | `server/discover` → `supportedVersions: ["2026-07-28"]` | modern session; no `initialize` or `initialized` ever sent; requests carry `_meta` |
| legacy stdio | `server/discover` → `-32601` | falls back; `initialize` sent with `2025-03-26`; requests carry no injected `_meta` |
| legacy stdio (pre-init error) | `server/discover` → `-32002 "not initialized"` | falls back to `initialize` |
| modern, version mismatch | `-32022` with `data.supported: ["2027-xx"]` | hard error naming the supported versions; **no** `initialize` fallback |
| discover ok, no mutual version | `supportedVersions: ["2025-11-25"]` | falls back to `initialize` |
| broken transport | probe and handshake both error | connection error surfaced (no infinite fallback) |
| result `_meta` tolerated | discover result carries `resultType`/server `_meta` | parsed, ignored gracefully |

### 2. HTTP-specific negotiation & headers (`stateless_http_test.go`)

- Modern server: asserts every POST carries `MCP-Protocol-Version:
  2026-07-28`, `Mcp-Method` matching the body method, correct `Mcp-Name`
  for `tools/call` (name) and `resources/read` (uri), `Accept` including
  both content types, and **no** `Mcp-Session-Id`; full
  `tools → call → read` flow succeeds without any `initialize` POST.
- Legacy server returning HTTP 400 (plain text body) on the probe: client
  falls back, `initialize` succeeds, session id round-trips, modern
  headers are absent.
- Legacy server returning HTTP 404 / 405: same fallback.
- Modern server returning HTTP 400 + `-32022` JSON-RPC body: error names
  supported versions; no `initialize` attempted.
- Header value encoding table tests: plain ASCII passes through; non-ASCII,
  leading/trailing whitespace, control characters, and values matching the
  `=?base64?...?=` sentinel pattern are base64-encoded per spec.
- Modern mode ignores a server-minted `Mcp-Session-Id` and never sends the
  legacy close DELETE.

### 3. resultType / MRTR (`call_test.go`, `resources_test.go`)

- `resultType: "complete"` and absent `resultType` → identical rendering.
- `input_required` + `requestState` only → automatic retry: new JSON-RPC
  id, `requestState` echoed byte-for-byte, then `complete` succeeds.
- `input_required` + `inputRequests` (elicitation) → `isError` output
  naming the unsupported interactive request; no retry loop.
- `input_required` with neither field → protocol error.
- Server loops `input_required` forever → bounded after 5 rounds with a
  clear error.
- Unknown `resultType` → error (spec: unrecognized values are invalid).
- Same matrix for `resources/read`.

### 4. Caching (`config_test.go`, `tools_test.go`)

- `tools/list` with `ttlMs: 1000` → cache treated stale after 1s (default
  10m does not apply).
- `ttlMs` larger than the default → default 10m cap still wins.
- No `ttlMs` (legacy server) → default TTL unchanged.
- `mcp tools --refresh` stores the new TTL.

### 5. Liveness (`tools_test.go`)

- `mcpPing` against a modern session sends `server/discover`, not `ping`.
- Against a legacy transport it still sends `ping`.

### 6. Daemon & integration (`daemon_test.go`, `integration_test.go`)

- Daemon spawning a modern stdio child: no `initialize` to the child;
  requests forwarded through the daemon reach the child with `_meta`
  injected.
- Daemon spawning a legacy child: unchanged handshake; forwarded requests
  untouched.
- End-to-end stdio integration test (Python fake server) runs in both eras.

### 7. Regression

- The full existing suite must pass. Existing legacy fixtures gain nothing
  but an extra `server/discover` → `-32601` round-trip, which exercises the
  fallback on every legacy-path test in the repo.
